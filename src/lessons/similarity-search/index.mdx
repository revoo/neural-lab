# Similarity Search

<LessonLink to="rag">Retrieval, in the RAG lesson</LessonLink>, starts with a question this lesson answers: given ten million vectors, how do you find the nearest ones without checking them all?

An embedding model turns every document, image or product into a vector, often 1,536 numbers long. With a few dozen of them you can simply compare the question with every vector in a loop, and the RAG lesson does exactly that with a 67-sentence manual.

What happens when your database grows to **10 million** 1,536D embeddings?

1. **Compute wall:** a brute-force scan computes `10,000,000 × 1,536 = 15.36 billion` multiply-adds *per single user query*!
2. **Memory wall:** storing 10 million `FP32` 1,536D vectors eats **57.22 GiB of RAM** — blowing past a single GPU or typical server node before you even build an index.

**<Term id="ann-search">Approximate Nearest Neighbour (ANN) search</Term>** trades a tiny sliver of recall (say `95%` instead of `100%`) for **10×–100× faster queries** and **4×–96× smaller RAM**. Every production vector database (FAISS, HNSWlib, pgvector, Qdrant) rests on three geometric ideas: **metric equivalence**, **partitioning / hashing**, and **quantised compression**.

## 1. Cosine, Dot Product, and Euclidean: one hidden identity

Before indexing anything, you have to pick a similarity score. Expand the squared Euclidean distance between two **unit-length** vectors ($\|\ca{a}\| = \|\cb{b}\| = 1$):

<Eq
  words="squared L2 distance on the unit sphere  =  2 × (1 − cosine similarity)"
  tex="\|\ca{a} - \cb{b}\|^2 = \|\ca{a}\|^2 + \|\cb{b}\|^2 - 2\,\ca{a}\cdot\cb{b} = 2\bigl(1 - \cg{\cos(\ca{a}, \cb{b})}\bigr)"
>
  - $\ca{a}, \cb{b}$ — two L2-normalised embedding vectors ($\|\ca{a}\| = \|\cb{b}\| = 1$)
  - $\cg{\cos(\ca{a}, \cb{b})} = \ca{a}\cdot\cb{b}$ — cosine similarity (identical to the dot product when both vectors have length 1)
</Eq>

That identity is why vector databases love normalising embeddings once at write time: on the unit sphere, **maximising Cosine similarity, maximising Dot Product, and minimising Euclidean distance always return the exact same top-$k$ list!** Without normalisation, long vectors hijack Dot Product — watch it happen live below.

## 2. IVF: partition the space with k-Means Voronoi cells

How do you avoid comparing a query against all 10 million vectors? **<Term id="ivf-index">IVF (Inverted File Index)</Term>** runs k-Means once at index time to divide the database into `nlist` Voronoi buckets around `nlist` centroids.

At query time:
1. Compare the query against just the `nlist` centroids (cheap!).
2. Open only the **`nprobe`** closest buckets and brute-force *only* the vectors inside them.

## 3. Random-Hyperplane LSH — and why data-aware IVF beats it

A classic alternative is **<Term id="lsh">Locality-Sensitive Hashing (SimHash)</Term>**: slice space with $b$ random hyperplanes through the origin and record a $b$-bit signature (`1` if on the positive side, `0` if negative). Two vectors separated by angle $\theta$ land on the same side of one random hyperplane with exact probability $1 - \theta / \pi$, so across $L$ independent $b$-bit tables:

<Eq
  words="P(candidate match in at least one table)  =  1 − (1 − (1 − θ/π)^b)^L"
  tex="\cg{P_{\text{hit}}}(\theta) = 1 - \Bigl(1 - \bigl(1 - \tfrac{\ca{\theta}}{\pi}\bigr)^{\cb{b}}\Bigr)^{\cc{L}}"
>
  - $\ca{\theta}$ — angle between query and database vector in radians ($0$ to $\pi$)
  - $\cb{b}$ — hash bits per table (more bits = tighter buckets, fewer false positives)
  - $\cc{L}$ — independent hash tables (more tables = higher recall on close pairs)
</Eq>

<Callout kind="info" title="Honest benchmark: IVF vs LSH (and HNSW in production)">
  On our exact 600 × 16D benchmark (60 held-out queries), **IVF (`nlist = 32, nprobe = 6`)** hits **91.3% Recall@5** by scanning **24.5%** (**4.1× faster**), beating **LSH (`b = 6, L = 16`)**, which needs **29.3%** scan (**3.4× faster**) for **90.7% Recall@5**. Why? Because k-Means adapts its boundaries to real clusters instead of slicing blindly with random planes. Modern databases also use **HNSW** (a multi-layer proximity graph, like an expressway skip-list over vectors) for even higher recall at `< 1%` scan, plus **<Term id="product-quantization">Product Quantisation (PQ)</Term>** — splitting each 1,536D vector into 64 sub-vectors and replacing each sub-vector with a 1-byte centroid ID, crushing 10M vectors from **57.22 GiB** down to **0.60 GiB** (**96× smaller!**).
</Callout>

<ForReal>

Production vector engines (**FAISS**, **Qdrant**, **Milvus**, **pgvector**) rarely pick just one technique — they compose them. A classic billion-scale FAISS index is `IVF65536,PQ64` (partition into 65,536 Voronoi cells, compress each vector to 64 PQ bytes so 1 billion vectors fit in ~64 GB RAM), often paired with a **two-stage re-ranker**: retrieve the top-200 approximate candidates from INT8/PQ/binary vectors in RAM, then fetch those 200 full-precision FP16/FP32 vectors from SSD to compute exact top-10 scores!

</ForReal>

## 5. Verifying unit-norm equivalence & 10M RAM in NumPy

```python
import numpy as np

# Exact proof: on unit vectors, ||a - b||^2 == 2 * (1 - cos(a, b))
rng = np.random.default_rng(0)
a = rng.normal(size=128); a /= np.linalg.norm(a)
b = rng.normal(size=128); b /= np.linalg.norm(b)

l2_sq = float(np.sum((a - b) ** 2))
from_cos = float(2.0 * (1.0 - np.dot(a, b)))
print(f"||a - b||^2 = {l2_sq:.8f} | 2(1 - cos) = {from_cos:.8f} | diff = {abs(l2_sq - from_cos):.2e}")

# 10M x 1536D vector database RAM across storage formats
N, D = 10_000_000, 1536
for name, b_per_vec in [("FP32", D*4), ("FP16", D*2), ("INT8", D), ("PQ-64", 64)]:
    print(f"{name:5s}: {N * b_per_vec / 1024**3:6.2f} GiB  ({D*4 / b_per_vec:4.0f}x compression)")
# ||a - b||^2 = 1.99468043 | 2(1 - cos) = 1.99468043 | diff = 2.22e-16
# FP32 :  57.22 GiB  (   1x compression)
# FP16 :  28.61 GiB  (   2x compression)
# INT8 :  14.31 GiB  (   4x compression)
# PQ-64:   0.60 GiB  (  96x compression)
```
